The Movement Is Nearly Free: KV-Cache Tier Transfer Is Not the Bottleneck in Long-Context Multiturn Serving

kleinrock · sglang KV-cache / serving, v0.31 · goodput@SLO rate sweep, Qwen3.5-122B, 2-tier (GPU HBM + 768 GB host) · a measurement study + a bounded-negative result (the eval's own metrics + per-request attribution + engine code-path analysis)
Abstract. Tiered-KV LLM servers (HiCache, LMCache, AttentionStore, Strata, Mooncake) keep the KV cache across a fast device tier (GPU HBM) and a large host tier (DRAM), and a great deal of engineering goes into hiding the transfer latency between them — asynchronous copy streams, prefetch pipelines, layout tricks. We ask, for a realistic long-context multiturn workload scored by goodput@SLO (max request rate with p99 TTFT ≤ 8 s), whether that transfer latency is actually on the critical path — and whether an anticipatory prefetch that overlaps the host→device restore with a running mega-document's prefill compute could raise goodput. We answer it from the evaluator's own captured metrics and per-request traces (and confirm the stock load_back_duration metric, widely read as a transfer cost, in fact times only the enqueue — the real copy runs later on a separate stream). Three findings. (1) The movement is enormous: at λ=7 the engine restores 1.04 billion and evicts 1.84 billion KV tokens across the tier boundary, while recomputing only 0.11 billion new tokens — the restore alone moves ~10× more KV than the engine produces (~26× counting eviction); the cache thrashes. (2) The movement is nearly free: end-to-end it is not exposed — among non-queued cache-hit requests the TTFT is flat against context length (a 40–100K-token cached context adds only ≤~0.17 s over the ~0.5 s scheduling floor, despite ~3 restores per request), and because such requests compute only their small new suffix there is almost no compute hiding the restore — so this exposed figure is already close to the full restore cost. (3) Therefore transfer overlap is a non-lever: the maximum benefit any prefetch/overlap mechanism could yield is bounded above by that restore cost (≤~0.17 s), which is <2% of the seconds-scale goodput knee (SRPF's p99 is 6.4 s at λ=5, 9.6 s at λ=7) — so we do not build it; we prove its ceiling. The p99 tail contains effectively no movement. We give the cost-hierarchy explanation (moving a KV token is ~40× cheaper than recomputing it), position the result against the tiering literature (whose transfer-hiding machinery targets a cost that, in this compute-bound long-context regime, does not bind), and close with a unified lever map for goodput@SLO: caching cannot fix the tail (companion paper P1), scheduling order can (companion paper P2), and tier movement is irrelevant to it (this paper). The value of tiering here is capacity — avoiding the 10× recompute — not latency-hiding.

1 Introduction

A tiered-KV LLM server keeps attention KV across two tiers: L1 in GPU HBM (fast, small) and L2 in host DRAM (slow-er, large). When a request's prefix has been evicted from L1 to L2, serving it requires a host→device (H→D) restore before the forward pass can attend to that prefix. The tiering literature treats this restore latency as a first-class problem: HiCache overlaps it on a dedicated copy stream, LMCache and AttentionStore build prefetch pipelines, Strata schedules transfers to hide them under compute, and all of them invest in layout choices to make the copy efficient. The implicit premise is that if you do not hide the transfer, it lands on the critical path and costs you tail latency.

We test that premise directly, on a workload where it should matter most: a Mooncake-style long-context multiturn mix (1553 conversations, 7163 turns, first-turn documents up to 192K tokens, Qwen3.5-122B on 8×H100, 2-tier KV with a 768 GB host tier), scored by goodput@SLO under an open-loop Poisson rate sweep λ ∈ {3,5,7,10}. Two companion results frame this one: the p99 TTFT tail that defines the metric is head-of-line queueing behind the cold prefill of a few unique mega-documents (P2), and it cannot be cached away because those documents are unique first-sight (P1). Here we ask the orthogonal question the tiering literature would ask: is the L1↔L2 movement itself a lever — and would hiding the restore latency under a running mega-document's compute raise goodput?

The answer is no, and the reason is quantitative and general. We find the engine moves an order of magnitude more KV than it computes, yet the movement is so cheap — decisively so as exposed on TTFT — that no amount of overlapping it can move a knee that lives at seconds. The transfer-hiding machinery is solving a problem this regime does not have.

2 Motivation: an enormous amount of KV moves across the tier boundary

If tier movement were ever going to bind, it would bind here. The evaluator captures the server's Prometheus metrics after every rate; aggregating the movement counters over the full sweep (Table 1) shows the tiering subsystem is extraordinarily busy. At λ=7 it performs 71,552 restore operations moving 1.04 billion KV tokens H→D and 161,656 eviction operations moving 1.84 billion tokens D→H, while the prefill engine recomputes only 0.11 billion new (non-cached) tokens over the same interval.

The cache thrashes: with a working set (~19M tokens) far exceeding L1+L2 (~10.7M), active conversation prefixes are evicted to L2 and restored to L1 repeatedly across turns, so the restore volume (1.04 B) far exceeds even the cached-token volume served (0.21 B at λ=7) — each cached prefix is restored several times. On any account of tiering cost that scales with bytes moved, this workload is a worst case. The question is whether that volume translates into latency on the critical path.

3 Background: where the restore sits on the prefill path

On a cache hit whose matched prefix is resident only in L2, sglang's UnifiedRadixCache.load_back() is invoked during prefill admission. It does not copy the KV; cache_controller.load() only allocates device slots and appends a CacheOperation to a load_queue. The actual copy is issued later by start_loading(), which merges the queued operations and runs a per-layer H→D copy on a dedicated load_stream; each layer records a CUDA event, and the forward pass consumes the KV lazily — get_key_buffer(layer_id) issues a cross-stream wait_event so the compute stream waits on the load stream per layer.

The overlap structure, and the gap. Within a batch, layer i−1's compute overlaps layer i's load (good pipelining). But the load is only enqueued after batch N is assembled, so it is not pre-issued during the prior batch's compute. When a mega-document occupies the prefill pipeline for ~13 s, the restores of the short requests waiting behind it do not begin until the mega-document clears. This is the gap an anticipatory prefetch would close: kick off the waiting requests' L2→L1 restores during the mega-document's compute (the H→D DMA engine is otherwise idle then), so they are resident the moment they are scheduled. That mechanism is the natural "hide the transfer" move; whether it is worth building is exactly what §5 decides. Note also that for a cache-hit request the forward pass computes only the small new suffix while the whole prefix must be loaded — so if restore were slow, it would be exposed (little compute to hide it behind). This is the case most favorable to the transfer-hiding thesis, and the one we measure.

4 Measurement methodology

The stock metric times the enqueue, not the DMA. observe_load_back_duration() wraps load_back(), whose body ends at the load_queue.append() — i.e. it measures index allocation + lock + enqueue, not the copy on load_stream. Its histogram (avg ~1.3 ms, Table 2) is therefore an enqueue cost, and cannot be read as the transfer time.

Timing the real copy (optional). For completeness we provide env-gated instrumentation (commit 3b2756b28, KL_DMA_TIMING=1, zero overhead and byte-identical behavior when off): two cuda.Events with enable_timing=True recorded on load_stream around the per-layer copy loop in start_loading(), drained lazily so timing never perturbs the serving path. This times the real H→D copy rather than the enqueue. We do not rely on it, however: the internal per-operation duration is not what a request actually pays, and the end-to-end measurement below bounds the exposed cost directly and more meaningfully.

The exposed cost (our primary measurement). What a request actually pays is the restore time exposed on TTFT. To isolate it we use the evaluator's per-request traces (prompt_len, ttft_ms, output_len) and isolate non-queued cache-hit requests (TTFT below the median, output ≤ 32 tokens = later conversational turns that hit their cached prefix) and ask whether their TTFT rises with prompt_len. A cache-hit later turn has a large cached prefix but a tiny new suffix, so any restore cost would show up as TTFT growing with context length. Flatness means the restore is not exposed.

Everything runs on the frozen evaluation contract (unchanged): full-decode Poisson sweep, NUMP=1553, max-concurrency 256, 2-tier --hicache-io-backend direct --hicache-mem-layout page_first_direct --hicache-write-policy write_through, on one --exclusive 8×H100 node.

5.2 The enqueue metric is not the transfer — and why the exposed cost bounds the DMA

A natural instinct is to read sglang:load_back_duration_seconds (Table 2) as the transfer latency. It is not. observe_load_back_duration() wraps UnifiedRadixCache.load_back(), whose body ends at cache_controller.load() — which only allocates device slots and appends a CacheOperation to the load_queue. The actual per-layer H→D copy runs afterwards in start_loading() on the load_stream. So the ~1.3 ms in Table 2 is enqueue overhead, not the DMA. (We also add an env-gated CUDA-event timer around the real copy, commit 3b2756b28, KL_DMA_TIMING; see §8. But it is not needed for our conclusion, and we do not rely on it, because the end-to-end measurement below bounds the transfer directly and more meaningfully.)

The transfer cost that matters is the part exposed on TTFT, and that is directly bounded by §5.3. Crucially, the requests that restore are cache hits: their forward pass computes only the small new suffix (a handful of tokens), while the entire matched prefix must be loaded H→D. There is therefore almost no compute for the restore to hide behind — so whatever a restore costs, a cache-hit request pays nearly all of it on its critical path. Consequently the exposed TTFT of §5.3 is already close to the full restore cost, not a small overlapped remainder. This makes the end-to-end measurement the right — and tightest — bound on the transfer, superseding any internal per-operation timer.

5.3 Exposed cost: TTFT is flat against context length

The decisive measurement is end-to-end. Among non-queued cache-hit requests at λ=5 (Table 3), TTFT is essentially flat from <1K to 100K tokens of cached context: the 15–40K bin is actually lower than the <1K bin, and the 40–100K bin is only ~90 ms above it. Since at λ=5 the engine performs ~3 restore operations per request (Table 1: 49,336 restores / 15,549 requests), these requests are restoring from L2 — and the restore still does not register on TTFT. The ~0.5 s floor is the scheduling/batch-formation overhead a 94-token request also pays.

5.4 Cost hierarchy: moving KV vs. recomputing it

Why is a billion-token movement free? Because moving a KV token is far cheaper than producing one. We read the ratio straight off the exposed measurement (§5.3): restoring a 100K-token cached prefix costs ≤~0.17 s — an effective restore rate of ≥~0.6 M tok/s — whereas recomputing those same 100K tokens of prefill costs ~7 s (a cold prefill runs at ~14K tok/s per stream: the largest document, 192K tokens, takes ~13.6 s). That is ~40× cheaper to move than to recompute. The tier boundary is cheap to cross precisely because the alternative it replaces — recompute — is expensive. This is the standard cache-hierarchy economics, and it is why tiering is worth doing; but it also means the transfer, not being the expensive part, cannot be the bottleneck. (Aggregate figures agree: the engine recomputes new KV at only ~38K–63K tok/s while sustaining the billion-token restore volume of Table 1.)

5.5 The non-lever result: a ceiling bound

Put the pieces together. An anticipatory-prefetch (or any transfer-overlap) mechanism can only remove a request's restore latency from its TTFT; its maximum possible benefit is therefore the restore's cost. That cost is bounded directly and tightly by the exposed measurement: a cache-hit request computes only its small new suffix, so it has essentially no compute to hide the restore behind (§5.2) — meaning the ≤~0.17 s it pays for a 100K-token cached context (§5.3) is already close to the full restore, not an overlapped remainder. And for the requests that actually define the tail the cost is smaller still — the p99 victims are tiny <1K-token requests (P2) whose restore is sub-millisecond. So a prefetch has at most ~0.17 s to give back to any request, and essentially nothing to give the tail. The goodput knee lives at seconds — SRPF's p99 is 6.4 s at λ=5 and 9.6 s at λ=7 (P2). Both bounds are far below it. Therefore:

Maximum achievable goodput gain from transfer overlap ≤ the full restore cost (≤~0.17 s, measured end-to-end) ≪ the seconds-scale knee. No prefetch/overlap mechanism can move goodput@SLO on this workload. The p99 tail contains effectively no movement: it is prefill compute of uncacheable mega-documents (P1) and head-of-line queueing behind them (P2). We therefore do not implement the prefetch — we bound its ceiling below threshold. (This is a stronger negative than A/B-testing one implementation: the bound rules out the entire mechanism class, not one design point.)

This mirrors, on a third axis, the bounded negatives of the companion papers — but where those required building and measuring a mechanism (P2's reserved lane, chunk-interleaving), here the measurement itself forecloses the mechanism.

6 Related work

Tiered KV and transfer hiding. HiCache (the sglang hierarchical cache), LMCache, AttentionStore (CachedAttention), and Strata all treat L1↔L2 (and L3/disk) transfer latency as a first-order cost and build machinery to hide it: asynchronous copy streams, prefetch/pipelining, and layout choices (page-first, layer-first) to make the copy contiguous. Mooncake's disaggregated store similarly optimizes KV transfer. Our result does not contradict theirs — it scopes it: in this compute-bound long-context regime on modern GPUs with a fast host DMA, the H→D restore is ≤~0.17 s exposed (and near-fully so, §5.2), so the transfer-hiding machinery, while correct, targets a cost that does not bind the tail. The lever they should reach for on this workload is capacity and scheduling, not transfer overlap. (The regimes where transfer does bind — slow interconnects, disk tiers, larger KV — are exactly the ones their designs were built for; §7.)

Prefix caching. vLLM/SGLang RadixAttention and prefix caching make cache hits cheap; our point is complementary: on this workload the hits are already cheap including their restore, and the tail is the misses (unique first-sight mega-documents, P1), which no movement mechanism touches.

CPU memory hierarchies. The cost hierarchy we measure (move ≪ recompute) is the classic reason caches exist; the twist for LLM serving is that the "recompute" (prefill) is so expensive that even a billion-token, thrashing tier movement is negligible beside it — the opposite of the CPU regime, where a cache miss (DRAM fetch) is expensive relative to the ALU work it feeds.

7 Limitations & when transfer does bind

  • Scoped to this regime. Our claim is: FP8 KV, a fast host DMA (direct + page_first_direct), 8×H100 with NVLink, a 768 GB host tier and no disk. Change any of these and transfer can re-enter the critical path: (i) a disk/L3 tier is orders of magnitude slower than DRAM and would expose latency (sglang's L3 prefetch machinery exists precisely for this); (ii) a PCIe-only node without fast H→D bandwidth; (iii) larger KV (FP16, more attention layers, MHA instead of GQA) increases bytes/token; (iv) cheaper compute (small models, short prompts) shrinks the recompute side of the hierarchy so movement becomes relatively more important. Our result is that in the long-context, compute-bound regime — the one that motivates large host tiers in the first place — transfer is not the lever.
  • Restore, not the whole tier subsystem. We measure the H→D restore that sits on the prefill critical path. Eviction (D→H backup) is off the critical path (asynchronous, write-through); its enqueue is ~1 ms (Table 2) and it is not TTFT-relevant, but we did not separately CUDA-event-time it.
  • Single hardware point. One node type; we did not sweep interconnect or KV dtype (they are fixed by the contract). The cost-hierarchy argument (§5.4) is what generalizes, not the absolute milliseconds.

9 Conclusion: the goodput@SLO lever map

Across three papers we have now characterized every axis by which a tiered-KV server could move goodput@SLO on this long-context multiturn workload:

The engineering implication is pointed: on a compute-bound long-context serving workload, do not spend effort hiding tier-transfer latency — it is nearly free. Spend the host tier's capacity to avoid recompute (worth ~10× the KV it moves), and spend scheduling to order the few expensive prefills. The movement is the part you can stop worrying about.
