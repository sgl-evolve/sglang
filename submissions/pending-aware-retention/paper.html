Pending-Aware KV Retention: Scheduler–Cache Co-Design for Multiturn LLM Serving

valiant · sglang KV-cache research (v0.31) · DRAFT — evaluation pending
Abstract. Hierarchical KV caches (HiCache-style L1 GPU + L2 host) are the standard way to reuse the growing prefix of a multiturn conversation and avoid re-prefilling it on every turn. Conventional wisdom holds that, once the tier sizes are fixed, the replacement order is a dead end — under in-order reuse LRU is within a fraction of a percent of Bélády's optimum. We show this conclusion breaks under concurrent multiturn load. When many conversations are interleaved, a conversation's cached prefix can be evicted by other requests during the gap between its turns, forcing a full recompute of a document that may be tens of thousands of tokens long — the single most expensive event on the prefill path. The loss is not eviction order (LRU ≈ Bélády among a fixed working set) but the eviction of prefixes whose reuse is imminent and already visible to the scheduler, a signal the cache ignores. We propose pending-aware KV retention: the cache protects the L2 residency of a conversation's prefix precisely while that conversation has an in-flight request the scheduler is holding, and releases it the instant the request is admitted. This is a scheduler↔cache co-design, not a replacement policy and not a config flag. A trace-driven analysis of the Mooncake-style 1:1:1 mix shows a realizable, non-oracle pending-aware policy recovers essentially the entire LRU→Bélády gap (up to +11 pp hit rate, ~30% fewer recomputes) at the cache capacities that arise in practice. 1  Introduction

Modern LLM serving is dominated by multiturn and agentic workloads: each turn re-sends the accumulated conversation, so the server can skip re-prefilling the shared prefix if its KV is still cached. On long-context workloads the prefix is enormous (a document of tens of thousands of tokens) and the new work per turn is tiny (one short question), so a single missed prefix — a recompute of the whole document — is by far the most expensive event on the prefill path and the dominant source of tail time-to-first-token (TTFT) under load.

HiCache tiers KV across L1 (GPU HBM) and L2 (host DRAM). When the working set exceeds L1+L2, the cache is genuinely over-subscribed and must evict. The prevailing view — and the explicit starting assumption of this protocol — is that eviction order is a solved problem: under in-order reuse LRU is within <0.1 pp of Bélády, so there is no headroom in "which victim to pick." We argue and demonstrate that this view misses the effect that actually matters under concurrency.

Contributions.

  • A trace-driven diagnosis showing that, under concurrent multiturn load, the cache's dominant loss is the eviction of conversation prefixes whose next turn is already in flight — not eviction order. We quantify a +5–11 pp hit-rate gap between LRU and Bélády at realistic capacities, overturning the "LRU ≈ Bélády" assumption in this regime.
  • Pending-aware KV retention: a mechanism that couples the cache's L2 retention to the scheduler's pending-request set. It is realizable and non-oracle (the scheduler already knows which conversations have a waiting request), capacity-bounded (it degrades gracefully to LRU when the pending set exceeds a budget), and lossless (it only changes which KV is retained, never what is computed).

2  Motivation (trace-driven)

All numbers below are computed directly from the frozen evaluation workload (mooncake_mix_v1.jsonl, the real-text Mooncake-style 1:1:1 mix of ShareGPT+LEval+LooGLE, 1553 conversations) with the model's own tokenizer.

2.1  The prefix is the workload

Each conversation is one long document (mean ≈ 11.8k tokens, p90 ≈ 28k, max ≈ 183k) followed by short follow-up questions (median ≈ 18 tokens); conversations average 4.6 turns (593 of 1553 are single-turn). The document prefix is reused across every turn of its conversation; there is no cross-conversation sharing. A cache that achieved perfect reuse would eliminate 80.9% of all prefill work (98.0M prompt tokens → 18.7M). Prefill is therefore the lever for throughput under load, and the value of the cache is enormous — but only to the extent it actually retains the prefixes that will be reused.

2.2  Continuation turns are load-/reuse-bound, and a miss is catastrophic

Because the new work per continuation turn is tiny, the turn's entire cost is decided by whether its prefix is a cache hit or a recompute. If the prefix (say a 12k-token document) has been evicted while the conversation was between turns, the server must re-prefill all 12k tokens — a spike two to three orders of magnitude larger than the turn's "real" work, which lands directly in the TTFT tail that defines goodput@SLO.

2.3  The loss is not eviction order — it is scheduler-visible imminent reuse

We replay the workload's issue order (an open-loop Poisson rate-λ pull with multiturn re-enqueue, matching the benchmark harness) through a page-level cache simulator at the model's real page size, and compare LRU, Bélády (oracle MIN), and a realizable protect-pending policy that simply refuses to evict a conversation whose next turn is currently in the system. Hit rate = cached / prompt tokens (the protocol's definition).

Two facts make this actionable. First, the gap is largest exactly at the capacities that occur in practice: at nominal capacity 10.7M the effective reuse-cache is smaller because ~255 concurrently-running requests occupy L1 (measured: L1 usage ≈ 0.95–0.97 under load), placing the operating point near the +11 pp knee. Second, the winning signal is free: the scheduler already tracks which conversations have a waiting request. protect-pending equals oracle admission-of-terminals in this workload because a conversation "with a pending turn" is exactly a conversation "with future reuse."

3  Design

Mechanism. While a request waits in the scheduler's queue, pin the host (L2) residency of its matched prefix so a running batch cannot evict it; release the pin the instant the request is admitted (its prefix is then protected by the normal running-request lock) or aborted. Pinning is bounded by a token budget (a fraction of L2); when the pending set exceeds the budget the policy falls back to LRU for the overflow — it never deadlocks eviction and never uses more than the fixed memory budget.

Why it is novel. It is not a replacement policy (LRU/LFU/GDSF/2Q): those choose a victim from a fixed candidate set, and §2 shows that choice is near-optimal already. It is not Strata-style cache-aware scheduling, which overlaps unavoidable loads with compute; here we prevent the eviction that turns a cheap reload into an expensive recompute. It is not a config flag (write-through/write-back, exclusive tiering): those change what is backed up, not whether an about-to-be-reused prefix survives contention. The primitive is a reuse-intent signal flowing from scheduler to cache.

Extension (v2, if headroom): server-queue pinning covers only the time a continuation spends in the server queue, not the client think/send gap before it arrives. A post-completion variant protects a just-finished conversation's leaf for a bounded horizon, covering that gap too. Evaluated as an ablation.

4  Implementation

Active cache: UnifiedRadixCache (the hybrid-Mamba + hierarchical path; hiradix_cache.py/hi_mamba_radix_cache.py are dormant). The mechanism is ~90 lines in managers/scheduler.py: pin at _add_request_to_queue via UnifiedRadixCache.inc_host_lock_ref(last_host_node) (capturing to_dec_params() so the release mirrors the acquire, incl. the mamba component's skip_lock_node_ids); release via a tick-start sweep over pinned requests no longer in the waiting queue (leak-proof across all admit/abort paths). No engine data-structure changes; no new tiers; budget = fraction × L2 size. Lossless by construction: the mechanism only changes which KV is retained. Commit: 28a775ae9 (evolve/valiant).

6  Related work

Strata (2025) attacks the data plane and scheduler: GPU-assisted I/O to defragment transfers and cache-aware scheduling to overlap load stalls with compute, making a loading-bound system compute-bound. It does not prevent the eviction that turns a reload into a recompute, and its data-plane fix (the kernel I/O path) is unavailable for hybrid-Mamba models, which are frozen to direct/page_first_direct by the Mamba host pool. Mooncake (FAST'25) and AttentionStore use a KV store and scheduling for reuse across requests; LMCache caches/streams KV; the SGLang HiCache blog contributes tiering, write policies, layer-wise load/compute overlap, and L3 prefetch staging. All treat retention as (recency-ordered) eviction plus (optional) prefetch. Our contribution is orthogonal: a scheduler-sourced reuse-intent signal that decides retention under contention, which the above leave to LRU. Classic cache-admission/replacement (TinyLFU, GDSF, 2Q, ARC) operates on recency/ frequency features; we instead use an exact, workload-structural signal (in-flight continuation).

7  Limitations & when it fails

  • Client-gap. Server-queue pinning protects only the server-queue window; a prefix evicted during the client think/send gap before its turn arrives is not recovered (addressed by the post-completion extension).
  • Capacity. When the pending set exceeds L2, pinning can only protect a budgeted subset; the gain shrinks toward LRU (Fig. 1, cap<8M).
  • Single-turn heavy workloads. If most conversations are one-shot, there is little pending reuse to protect and the mechanism is a no-op (safe).
