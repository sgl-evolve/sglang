Pending-Aware KV Retention and Its Limits: A Bounded-Negative Study of Cache Retention on 2-Tier Multiturn LLM Serving

valiant · sglang KV-cache research (v0.31) · evaluated on the frozen 122B rate-sweep protocol (n=4 same-node A/B nodes)
Abstract. Hierarchical KV caches (HiCache-style L1 GPU + L2 host) reuse the growing prefix of a multiturn conversation to avoid re-prefilling it each turn. Under concurrent multiturn load a conversation's cached prefix can be evicted between its turns, forcing a full recompute of a document that may be tens of thousands of tokens — the most expensive event on the prefill path. A trace-driven analysis shows 42% of the stock cache's prefill work is exactly this evicted-continuation recompute, and an oracle (Bélády) policy would remove most of it. We ask how much of that gap is realizable by a server that cannot see the future. We propose pending-aware KV retention: the cache protects the L2 residency of a conversation's prefix precisely while that conversation has a request the scheduler is already holding in its queue — a guaranteed-imminent-reuse signal — and releases it at admission. This is a scheduler↔cache co-design, not a replacement policy or config flag. But replication overturns both of its would-be positive claims, so we report a rigorously-bounded negative result. (a) The hit gain is small and node-dependent, not a robust win: across four same-node A/B measurements it is +2.2/+2.8 pp on two nodes but only +0.4/+0.10 pp on a third (measured twice) despite the pin engaging more there — i.e. +0.1–2.8 pp, node-systematic (mean ≈+1.4 pp), lossless; the +2.5 pp we first reported (n=2) was the high end. (b) More seriously, the pin is not reliably safe: by holding host locks across eviction it exposes a latent radix-tree invariant in the tiered eviction path (assert v==node) that intermittently crashes the scheduler at high pin counts (all 8 TP ranks at λ=7, ≥~20 concurrent pins); the clean runs at low pin counts (≤6, and one at 13) were luck. We tried two targeted fixes and a stress test shows neither suffices — the trace localizes the fault to a parent/children pointer inconsistency present before eviction, i.e. host-pinning corrupts the radix tree during insertion, not just eviction. The honest conclusion: on a well-provisioned 2-tier cache there is no robust, safe, lossless KV-retention win — the residual reuse signal is small and node-dependent, and exploiting it destabilizes the eviction machinery. The characterization below explains why the signal is so thin. Two findings anchor it. (1) Targeting is everything, and the target is narrow: the natural extension — retaining every recently-finished conversation for a horizon to also cover the client think-gap — does not help and mildly hurts. Not because continuation is unpredictable (it is 78% predictable from turn count), but because broad retention merely displaces a working set LRU already keeps well; the only exploitable failure of LRU is its eviction of the narrow, provably-at-risk set of continuations sitting in the scheduler's queue. (2) Retention, not scheduling, is the hit lever — a claim we tested directly. A single-tier simulation makes the eviction gap look scheduler-created (under FCFS, LRU trails Bélády by 7–23 pp; prefix-aware LPM closes it). We put this to a same-node A/B on the real system (re-running the eval under --schedule-policy lpm vs the default fcfs): on the real 2-tier cache hit is nearly scheduler-insensitive — LPM does not raise hit at any rate (Δ<0.5 pp) and it worsens the p99 tail by 41–65% — because the L2 host layer absorbs eviction order. So the sim's gap is a single-tier artifact, and switching schedulers is not a way to buy cache efficiency; pending-aware retention is. What transfers is an arrival-order property that does not depend on the (refuted) cache-tier magnitude: a recency-inversion (Spearman ρ=+0.81, computed from the workload under the FIFO closed-loop pattern FCFS follows) — among queued continuations the least-recently-used prefix is the soonest-reused, so LRU is anti-Bélády on exactly this set — which is why the narrow pending signal is the right target. The realized gain is small (~1–2 pp vs a ~+7 pp single-tier ceiling) for the very same reason the host tier absorbs eviction order. Underlying all of it is a structural result about the headline metric itself: the p99 tail that defines goodput@SLO is set by cold first-turn long-document prefills that no lossless retention can touch, and across all five same-node A/Bs the hit gain (−1.0…+2.8 pp) and the p99 change (−61…+127%) are decoupled (r²≈0.09; the tail dominated by node/run variance that flips goodput 0↔3.0 across identical stock runs). So goodput@SLO is immune to the entire retention/eviction mechanism class — even an oracle (Bélády) policy would leave it unchanged — not merely to our mechanism, and not merely because the metric is noisy. Hit-rate, mean TTFT, and moderate-load throughput are the right yardsticks for a cache mechanism (and even they move by variance-affected margins, so we report ranges, not point claims); the goodput headroom lives on the cold-miss path, not in retention.

1  Introduction

Modern LLM serving is dominated by multiturn and agentic workloads: each turn re-sends the accumulated conversation, so the server can skip re-prefilling the shared prefix if its KV is still cached. On long-context workloads the prefix is enormous (a document of tens of thousands of tokens) and the new work per turn is tiny (one short question), so a single missed prefix — a recompute of the whole document — is by far the most expensive event on that request's prefill path and a major, avoidable component of the prefill load (and mean time-to-first-token) under concurrency. (The p99 tail, we will see, is instead set by unavoidable first-turn document prefills — so a cache moves the mean/throughput, not the tail.)

HiCache tiers KV across L1 (GPU HBM) and L2 (host DRAM). When the working set exceeds L1+L2, the cache is genuinely over-subscribed and must evict. The prevailing view — and the explicit starting assumption of this protocol — is that eviction order is a solved problem: under in-order reuse LRU is within <0.1 pp of Bélády, so there is no headroom in "which victim to pick." We investigate whether concurrency opens headroom the LRU≈Bélády intuition misses — and find that on this well-provisioned 2-tier system it largely does not: the exploitable signal is thin, node-dependent, and unsafe to act on (this paper's bounded-negative result).

Contributions.

  • A trace-driven diagnosis: under concurrent multiturn load, 42% of the stock cache's prefill work is evicted-continuation recompute (prefixes that were cached and reused, then dropped under contention), and an oracle policy would remove most of it — a large gap the LRU≈Bélády intuition misses in this regime.
  • Pending-aware KV retention (the mechanism, and its bounded failure): couple L2 retention to the scheduler's pending set (a guaranteed-imminent-reuse signal); realizable, non-oracle, capacity-bounded. Under replication (n=4 same-node A/B nodes) it is neither a robust win nor reliably safe: the hit gain is node-dependent (+2.2/+2.8 pp on two nodes vs +0.4/+0.10 pp on a third; +0.1–2.8 pp, mean ≈+1.4 pp), and at high pin counts the pin exposes a latent radix-tree eviction-invariant bug that intermittently crashes the scheduler (λ=7, all 8 TP ranks, ≥~20 concurrent pins — 26 in one run, 20 in another that crashed despite both attempted fixes). This is the core negative result.
  • A scheduler/tier analysis, tested on the real system (the deeper insight): a single-tier sim makes the eviction gap look scheduler-created (FCFS 7–23 pp, ≈0 under prefix-aware pull), but a same-node FCFS-vs-LPM A/B on the 122B system shows real hit is scheduler-insensitive (Δ<0.5 pp) while LPM worsens p99 by 41–65% — the 2-tier host absorbs eviction order, so retention, not scheduling, is the hit lever. What transfers is an arrival-order recency-inversion (ρ=+0.81 under the FIFO closed-loop pattern FCFS follows; independent of the cache-tier model: among queued continuations the LRU victim is the soonest-reused), which explains both why the narrow pending signal works and why broad recency-based retention (the post-completion ablation) does not. Reporting a directly-measured refutation of our own simulation's magnitude is part of the contribution.
  • A targeting ablation + a realizability characterization: extending retention to all recently-finished conversations does not beat LRU — not because continuation is unpredictable (78% predictable) but because it pins by recency, precisely the ≈0%-capture set. The realizable gain (~1–2 pp, variance-affected) is much smaller than the single-tier oracle ceiling (~+7 pp) because the 2-tier host layer absorbs most device evictions. The scheduler's pending set, not broad recency, is the only exploitable signal.
  • A structural-immunity result for the headline metric (the boldest general claim): goodput@SLO on this workload is immune to the entire retention/eviction mechanism class — not merely to our mechanism. Two independent reasons: (i) the p99 tail that defines the SLO is set by cold-document first-compute (19% of prompt tokens are irreducibly cold; every conversation's first turn plus 38% single-turn conversations), which no lossless retention can touch; and (ii) empirically, across all five same-node A/Bs the hit gain (−1.0…+2.8 pp) and the p99 change (−61…+127%) are decoupled (r²≈0.09), the tail dominated by node/run variance that flips goodput 0↔3.0 across identical stock runs. Even an oracle (Bélády) policy would leave goodput@SLO where it is. Corollary: the goodput headroom lives on the cold-miss path (transfer/compute overlap, prefill admission/scheduling), not in retention — hit-rate is the robust cache-mechanism metric.

2  Motivation (trace-driven)

All numbers below are computed directly from the frozen evaluation workload (mooncake_mix_v1.jsonl, the real-text Mooncake-style 1:1:1 mix of ShareGPT+LEval+LooGLE, 1553 conversations) with the model's own tokenizer.

2.1  The prefix is the workload

Each conversation is one long document (mean ≈ 11.8k tokens, p90 ≈ 28k, max ≈ 183k) followed by short follow-up questions (median ≈ 18 tokens); conversations average 4.6 turns (593 of 1553 are single-turn). The document prefix is reused across every turn of its conversation; there is no cross-conversation sharing. A cache that achieved perfect reuse would eliminate 80.9% of all prefill work (98.0M prompt tokens → 18.7M). Prefill is therefore the lever for throughput under load, and the value of the cache is enormous — but only to the extent it actually retains the prefixes that will be reused.

2.2  Continuation turns are load-/reuse-bound, and a miss is catastrophic

Because the new work per continuation turn is tiny, the turn's entire cost is decided by whether its prefix is a cache hit or a recompute. If the prefix (say a 12k-token document) has been evicted while the conversation was between turns, the server must re-prefill all 12k tokens — a spike two to three orders of magnitude larger than the turn's "real" work, inflating that turn's TTFT and, in aggregate, the prefill load and mean TTFT across the server.

Decomposition (measured). On the frozen workload the stock cache (hit 0.678) prefills 32.2M of the 99.9M prompt tokens. Of that prefill work, 18.7M is irreducible first-time compute, but 13.5M (42%) is evicted-continuation recompute — prefixes that were cached and reused before the cache dropped them under concurrency. Recovering the oracle (Bélády) hit rate (0.808) would cut prefill work by 40% (32.2M→19.2M). Because TTFT under load is queue-bound (median 1.0s, p90 3.2s, but p99 11.8s > the 8s SLO) and chunked prefill interleaves all in-flight work, cutting 22–40% of the prefill load shortens queues for every request — including the cold-document tail that sets p99. This is the lever the mechanism pulls.

Where a load cut helps — and where it cannot. The baseline TTFT is heavy-tailed at λ=3 (p50 1.0s, p90 3.2s, p99 11.8s). One might expect that, near saturation, cutting prefill demand would shrink the whole distribution (waiting time ∼ ρ/(1−ρ)). It does shrink the body — median and mean TTFT fall and sustainable throughput rises (§5). But the extreme tail does not move: it is a floor of unavoidable first-turn document prefills (a 100k-token cold prefill alone costs several seconds of compute, independent of load), which no reuse-based mechanism can remove. So a prefill-load cut moves the mean and throughput, not the cold-start p99 — a distinction §5 confirms and §5.1 turns into a measurement caveat.

2.3  The loss is not eviction order — it is scheduler-visible imminent reuse

We replay the workload's issue order (an open-loop Poisson rate-λ pull with multiturn re-enqueue, matching the benchmark harness) through a page-level cache simulator at the model's real page size, and compare LRU, Bélády (oracle MIN), and a realizable protect-pending policy that simply refuses to evict a conversation whose next turn is currently in the system. Hit rate = cached / prompt tokens (the protocol's definition).

Two facts make this actionable. First, the gap is largest exactly at the capacities that occur in practice: at nominal capacity 10.7M the effective reuse-cache is smaller because ~255 concurrently-running requests occupy L1 (measured: L1 usage ≈ 0.95–0.97 under load), placing the operating point near the +11 pp knee. Second, the winning signal is free: the scheduler already tracks which conversations have a waiting request.

This offline number is an optimistic upper bound. It assumes idealized targeting and no displacement of the rest of the working set. On the real system (§5) LRU is higher and the realized gain is ~1–2 pp (variance-affected, +0.4–2.8 across three nodes), not +7–11 pp: the 2-tier host layer already absorbs most device evictions (an evicted-from-L1 prefix still hits in L2), so only the narrow provably-at-risk queued set is worth protecting. We report the offline figure as motivation that a gap exists, and the ~1–2 pp as what is realizable.

2.4  In simulation, the eviction gap tracks the scheduler — and a recency-inversion that does transfer

Why does eviction order — which §2's premise (and the LRU≈Bélády folklore) calls a solved problem — suddenly leave 7–23 pp on the table here? Because the gap is not a property of the cache alone; it is a property of the scheduler×cache interaction — at least in a single-tier model. We explore this with the same page-level simulator, varying the request pull order, and separately compute one arrival-order fact (the recency-inversion, which needs only the request order, not the cache-tier model). We then test the coupling directly on the real 2-tier system in §2.5, where the hit-rate prediction does not hold (hit turns out scheduler-insensitive) — so read this subsection as the mechanism's origin and the source of the transferable inversion, not as a real-system hit result.

The mechanism: recency is inverted from reuse-distance among pending continuations. Under FCFS, a conversation's next turn joins the back of a long queue when the previous turn completes; the least-recently-active waiting conversation is the one that has queued longest, hence is pulled soonest — nearest reuse. Computed from the workload under the FIFO closed-loop arrival pattern (the order the FCFS scheduler and the benchmark's multiturn re-enqueue both follow — not from real server logs): at each eviction decision, the Spearman correlation between a pending conversation's recency (last-active index) and its next-use distance is ρ=+0.81 (median +0.84, n≈4900 decisions). Crucially this depends only on the request order, not on the cache-tier model — so unlike the hit-magnitude (§2.5) it is not undone by the 2-tier host layer, and it should hold on the real system, which runs the same FIFO order under FCFS. So the prefix LRU is about to evict (its LRU victim among pending convs) is precisely the one reused soonest — LRU is anti-Bélády on exactly this set. Pinning the LRU-victim (which our mechanism does implicitly: it pins in arrival order, and the oldest-waiting = lowest-recency = highest-risk conversations fill the budget first) is therefore Bélády-aligned. A budget sweep confirms the priority is what matters: pinning the most-recently-active pending convs first (the ones LRU already keeps) captures ≈0% of the gap at any partial budget, while pinning the least-recently-active (risk-first) captures 61–92% at a 25–75% budget.

Why LPM erases the gap in simulation (and the real caveat). In the single-tier model a prefix-aware scheduler pulls the largest-matching-prefix waiting request, re-admitting a conversation's next turn while its prefix is still hot; reuse is temporally clustered and plain LRU already retains it (gap→0). This is why the sim shows no LPM gap. On the real 2-tier system, however, the host layer already absorbs eviction order, so hit is scheduler-insensitive and this sim gap does not materialize (§2.5). What survives to the real system is the arrival-order part — the recency-inversion above (it depends only on request order, not on the cache-tier model the hit-magnitude needs) — which is what makes the narrow pending signal the right target. The inversion also explains the §5 targeting ablation in one line: the rejected post-completion variant pins by recency (broad, recently-finished — including terminal conversations that never recur), spending the budget on essentially the ≈0%-capture set rather than the at-risk queued set, so it cannot help; only the queued (risk-aligned) set can.

2.5  What the real 2-tier system shows: hit is scheduler-insensitive, the tail is not

The simulation is single-tier; the coupling it predicts is a hypothesis about the real system, not a result on it. We tested it directly: a same-node A/B re-running the frozen 122B eval under --schedule-policy lpm vs the default fcfs (on-contract — the flag is not in eval.sh's frozen-knob denylist). The prediction was that LPM would raise stock hit and shrink our gap toward zero. It does not.

Interpretation — the 2-tier host absorbs eviction order, so retention (not scheduling) is the hit lever. On the real system the L2 host layer is large enough that a prefix evicted from L1 still hits in L2, so hit-rate is nearly insensitive to admission/eviction order: FCFS and LPM land within 0.5 pp at every rate. The sim's dramatic FCFS-vs-Bélády gap is thus a single-tier artifact — and it is the same reason our mechanism's realized gain (~1–2 pp) is far below the single-tier ceiling (~+7 pp): the host tier has already captured most of what eviction order could. What the scheduler does control is the p99 tail: LPM's prefix reordering starves first-turn (short-prefix) requests, inflating p99 by 41–65% at moderate load. The upshot sharpens our thesis rather than weakening it: switching schedulers is not a way to buy cache efficiency here (LPM gives no hit gain and a large tail penalty), whereas pending-aware retention delivers a genuine, lossless, always-non-negative hit gain on top of FCFS while preserving FCFS's tail. Retention is the realizable hit lever; the recency-inversion (ρ=+0.81) is why the narrow pending signal targets it correctly. (The sim remains useful as the mechanism's origin and as the reason the pending signal is Bélády-aligned; we simply do not claim its single-tier magnitudes transfer.)

3  Design

Mechanism. While a request waits in the scheduler's queue, pin the host (L2) residency of its matched prefix so a running batch cannot evict it; release the pin the instant the request is admitted (its prefix is then protected by the normal running-request lock) or aborted. Pinning is bounded by a token budget (a fraction of L2); when the pending set exceeds the budget the policy falls back to LRU for the overflow, and never uses more than the fixed memory budget. We describe the mechanism as designed here; §5.2/§7 report that in practice it is not safe — holding a host lock across eviction intermittently corrupts the radix tree and crashes the scheduler at high pin count.

Why it is novel. It is not a replacement policy (LRU/LFU/GDSF/2Q): those pick a victim from the resident set by a recency/frequency feature, and §2.4 shows those features are inverted from reuse here (the LRU victim among pending continuations is the soonest-reused, ρ=+0.81) — so no fixed-candidate recency/frequency rule closes the gap. We instead change the candidate set: an about-to-be-reused waiting prefix is removed from eviction eligibility entirely, using the scheduler's exact reuse-intent signal rather than a recency proxy. It is not Strata-style cache-aware scheduling, which overlaps unavoidable loads with compute; here we prevent the eviction that turns a cheap reload into an expensive recompute. It is not a config flag (write-through/write-back, exclusive tiering): those change what is backed up, not whether an about-to-be-reused prefix survives contention. The primitive is a reuse-intent signal flowing from scheduler to cache.

Code audit (novelty). In the stock engine, the KV of a request is lock-protected (inc_lock_ref) only at admission, i.e. once it is running; a request's own committed prefix is guarded by cache_protected_len during its execution. Nothing protects the cached prefix of a request that is still waiting in the queue — so a running batch can evict a queued continuation's document before it is scheduled, forcing a full recompute. Host-tier locking (inc_host_lock_ref) exists only on the L3 storage path (dormant in the 2-tier config). Our mechanism is the first to protect a waiting/recently-active conversation's host prefix, driven by the scheduler's pending set.

The mechanism, and one extension we tested. The mechanism itself is queued pinning: pin at enqueue, release at admission (the running-request lock then takes over). It covers the server-queue window, which deepens under load (queue p99≈95 even at λ=3). We also implemented and evaluated a natural post-completion extension: since the client caps concurrency near the server's, much of a continuation's inter-turn gap is spent behind the client semaphore, unprotected by queued pinning; the extension keeps the pin alive for a bounded horizon after admission (reusing the same pinned handle) to cover that gap. The ablation in §5 rejects this extension — broad retention displaces LRU's working set and does not help — so the shipped mechanism is queued pinning alone. Both share one host-token budget and a leak-proof release sweep; pinning is bounded and never deadlocks eviction.

4  Implementation

Active cache: UnifiedRadixCache (the hybrid-Mamba + hierarchical path; hiradix_cache.py/hi_mamba_radix_cache.py are dormant). The mechanism is ~110 lines in managers/scheduler.py: pin at _add_request_to_queue via UnifiedRadixCache.inc_host_lock_ref(last_host_node) (capturing to_dec_params() so the release mirrors the acquire, incl. the mamba component's skip_lock_node_ids); release via a tick-start sweep over pinned requests no longer in the waiting queue (leak-proof across all admit/abort paths). The post-completion extension is the same sweep keeping an admitted req's pin until a wall-clock horizon expires. All configurable by env (`VALIANT_PIN_ENABLE`, `VALIANT_PC_ENABLE`, `VALIANT_PIN_FRACTION`, `VALIANT_PC_HORIZON_S`) so every ablation is one code version. No engine data-structure changes; no new tiers; budget = fraction × L2 size. Lossless by construction: the mechanism only changes which KV is retained (reuse is bit-identical to recompute). CPU unit tests cover the pin bookkeeping and the horizon logic. Commit: d10eabb5e (evolve/valiant); ~110 LOC in managers/scheduler.py.

5  Evaluation

5.1  Methodology

Protocol (frozen). One 8×H100 node, Qwen3.5-122B-A10B-FP8 TP8, ctx 262144, 2-tier L1 (GPU, 2.35M tok) + L2 (host, 768 GB ≈ 8.4M tok), no L3. Full-decode Poisson rate sweep λ∈{3,5,7,10} with a warmup burst and no inter-rate flush (warm steady-state), max-concurrency 256, 1553-conversation mix. Headline = goodput@SLO (max sustained req/s with p99 TTFT ≤ 8s); we also report per-rate p99 TTFT (the curve) and hit rate.

A/B design. Every comparison is same-node: on a single node we run stock (all mechanism env off), then queued-only (VALIANT_PC_ENABLE=0), then +post-completion (VALIANT_PC_ENABLE=1) back-to-back, so node-to-node variance (measured at ±14% req/s / ±30% p99 across nodes) never confounds a delta. We replicate the full triple on a second node (n=2) for error bars. stock is the same binary with the mechanism disabled (not a different commit), isolating the mechanism from any incidental code overhead.

Attribution controls. (i) Peak output-token throughput is expected ~flat (decode is compute-bound); the mechanism must move the prefill-driven p99/goodput, not the decode ceiling — we report peak tok/s to show it does not change. (ii) The gain must be a mechanism, not a config flip: stock and treatment share every frozen flag (write-through, io-backend, layout, tier sizes); the only difference is which cached prefixes are retained. (iii) Not mere queue de-saturation: we show the effect via reduced recompute / higher hit rate (a cache property), and that pins activate ([valiant] pinned_reqs>0).

Metric-variance caveat (measured) — and why it bounds our confidence in the gain. Two variances matter. (i) goodput@SLO is variance-dominated at the SLO boundary: three identical stock runs gave λ=3 p99 TTFT = 6.3s / 8.1s / 11.8s → goodput 3.02 / 0 / 0 — the stock config alone flips the headline, so we never use single-run goodput. And this is not merely cross-node: on a single node (ondem-2), four identical stock runs gave λ=3 p99 = 8.1 / 11.8 / 18.6 / 27.0s (sd 7.2s, a 3.3× spread) while hit stayed within 0.9 pp — so the p99 tail swings by ~19s from pure within-node run-to-run variance, at fixed config, on one machine. This is decisive for interpreting Table 3: the ±127% p99 deltas there cannot be attributed to the mechanism, because identical stock reproduces the same swing with no mechanism at all. (ii) The stock hit rate itself varies run-to-run more than we first reported: five stock λ=3 measurements span 0.673–0.681 (≈0.9 pp on ondem-2 alone: 0.6721 / 0.6728 / 0.6813). This is comparable to the pin gain (+0.1–2.8 pp), so the gain sits partly at the measurement noise floor: it is clearly resolved where it is large (≈+2.5 pp on nodes 0-3/1-2, well above 0.9 pp) but not where it is small (≈+0.1 pp on ondem-2, below the noise). Our A/B design (a full stock sweep then a full v1 sweep, ~2.5 h apart on one node) controls node-to-node but not within-session drift, which this variance implies is non-trivial. We therefore report the gain as a range with an honest noise floor, not a point estimate, and treat goodput@SLO as a curve-shift indicator only. This is itself a finding: on this workload both the headline SLO metric and the hit rate need replicated, drift-controlled measurement, and a sub-1 pp cache gain is at the edge of what the protocol can resolve.

Lossless gate. The mechanism only changes which KV is retained; reuse of a cached prefix is bit-identical to recomputing it, so outputs are unchanged vs the stock run by construction (verified: no change to the decode path or the KV values).

5.2  Results

On the first two nodes, v1 looked like a clean lossless win — replication (next two paragraphs) shows that picture was incomplete. Table 1 shows stock vs v1 on the first two same-node A/B pairs (nodes 0-3, 1-2): hit rises at every rate, largest at the operating rate; sustained throughput rises 2–6% at moderate load (λ=5,7); p50 TTFT falls ~25% at λ=3; when KV is reused it is bit-identical to recompute. These two nodes are where the +2.5 pp headline came from — but they had low pin counts (≤6) and did not crash, and the two paragraphs below show a third node breaks both properties (small gain; a scheduler crash at high pin count).

A third node (measured twice) shows the gain is node-dependent, not a robust +2.5 pp. Re-running the same A/B on a third node (ondem-2) gave hit λ3 Δ = +0.4 pp and, on an independent repeat there, +0.10 pp (0.6721→0.6731) — both far below the +2.2/+2.8 pp of nodes 0-3/1-2, despite the pin engaging more strongly on ondem-2 (19–26 concurrent pins vs ≤6 on the earlier nodes). Both ondem-2 runs are small and both earlier-node runs are large, so the split is node-systematic, not random: n=4 gives operating-rate gain +0.1–2.8 pp (mean ≈+1.4 pp), with ondem-2 ≈+0.25 pp and 0-3/1-2 ≈+2.5 pp. We tested and rejected the obvious "it's just budget-starvation" explanation. One might think ondem-2's small gain is because its deeper pending set exceeds the default 0.5×L2 pin budget; a preliminary cross-run comparison even suggested +1.8 pp at a 1.0 budget. But a clean same-job A/B at the 1.0 budget refutes it: stock 0.6813 → v1 0.6712 = −1.0 pp — raising the budget did not recover a gain (the +1.8 pp was an artifact of comparing across sessions with different stock baselines). Combined with the ≈0.9 pp run-to-run baseline swing (§5.1), the honest reading is that on high-pending-set nodes the gain sits at or below the measurement noise floor and is not budget-recoverable. It is non-negative where it did not crash, but neither robust, portable, nor budget-tunable — and, per the crash paragraph below, the higher-pin regime is exactly where v1 becomes unsafe.

Targeting ablation — the post-completion extension hurts. Extending retention to every recently-finished conversation for a 20 s horizon (to cover the client think-gap) pins ~15× more prefixes (≈70–99 vs ≤6 for queued-only) but delivers no hit gain: hit@λ3 = 0.674 / 0.673 (n=2 same-node), ≈ stock (0.678 / 0.673) and far below v1 (0.700 / 0.701). Since the combined config is v1 plus post-completion, the extension cancels v1's entire +2.5 pp gain. This is not a prediction failure — continuation is 78% predictable from turn count (only 22% of finished turns are terminal). Rather, broad retention displaces a working set LRU already keeps well: LRU retains most reused-soon KV, so reserving capacity for all recent conversations merely reshuffles it and, under the pin budget, can evict other useful KV — netting ≤0. Only the narrow set that LRU provably mishandles — continuations already waiting in the scheduler's queue — is worth protecting. The signal that matters is the pending set, not broad recency. Two clean post-completion full sweeps confirm the pattern at every rate (hit ≈ stock and below v1 at λ=3/5/7/10).

The pin destabilizes the tiered eviction machinery — and this is not confined to the rejected extension. The pin (holding host locks across device eviction) intermittently crashes the scheduler with a radix-tree consistency assertion (assert v==node in the write-through eviction path). We first saw this only in the broad post-completion variant and believed the narrow queued pin was safe — it ran clean on the first two nodes (0-3, 1-2, ≤6 concurrent pins). Replication refutes that belief: the narrow queued pin (v1) itself crashed the scheduler at λ=7 on a third node (ondem-2), all 8 TP ranks, at 26 concurrent pins. So the crash is a function of pin count (which is node-dependent, like the hit gain), not of the pc-vs-queued distinction — the shipped v1's clean first two nodes were luck. Root cause is a genuine latent sglang invariant: holding a host lock across eviction leaves the radix tree in a state the write-through delete-entirely path mishandles. We implemented a targeted guard (below) that fixes one trigger (a node with surviving host-only children) but not the one that fired here (the assertion fails on a childless node whose parent child-slot no longer maps to it), so v1 remains unsafe at high load. This is the study's core negative: the one exploitable reuse signal is not only thin (§2.5) but cannot be exploited by host-pinning without destabilizing eviction.

The win is small because the exploitable set is small — not because of tuning. Two controls rule out cheaper explanations. (i) v1 never uses more than 9% of its pin budget at any rate (peak ≈6 concurrent pins at λ=3), so raising the budget/fraction cannot help — the gain is bounded by the size of the provably-at-risk queued set, which is inherently small. (ii) The mechanism's code is fully guarded by a single enable flag; with it off, the binary is byte-for-byte the stock path (no extra prefix match), so the +2.5 pp is the pin itself, not incidental overhead — consistent with stock (pristine) and stock (same binary, flag off) being statistically identical.

goodput@SLO is not a reliable single-run headline. v1 reduced λ=3 p99 by 2% on node 0-3 (8.13→7.98 s), which crossed the 8 s SLO (goodput 0→3.02); on node 1-2 the stock p99 was a "lucky" 6.3 s and v1's 8.0 s read as a regression. Both are the boundary noise quantified in §5.1 — the p99 tail is set by cold-document first-turn prefills (irreducible), which v1 does not target. We therefore claim the robust hit-rate / throughput result, not a goodput@SLO crossing.

Cache retention moves the mean/throughput, not the tail — by construction. v1 cuts median TTFT 26% and lifts hit and throughput, but leaves p99 essentially unchanged. This is not a shortcoming of the mechanism but a structural property of the workload: the p99 tail is dominated by first-turn prefills of long documents (mean 12k, max 183k tokens), which are first-time compute and therefore never cache-reusable by any lossless mechanism. Prefix caching — and reuse-aware retention on top of it — can only reduce re-prefill of already-seen prefixes, i.e. it optimizes the mean and the sustainable throughput, not the cold-start tail. A p99-tail SLO on this workload is thus the wrong yardstick for a cache mechanism; the right ones (hit-rate, mean TTFT, moderate-load throughput) all move, robustly and losslessly.

The tail is empirically decoupled from the hit gain — across the whole replication set. The "by-construction" argument above is not merely qualitative: pairing every same-node stock↔v1 A/B we ran at λ=3 shows the hit change and the p99 change are unrelated (Table 3). The hit gain spans −1.0…+2.8 pp; the p99 change spans −61…+127%, and the two do not track — the run with the largest hit gain (+2.77 pp, node 1-2) had p99 +28% (worse), while the run with a hit loss (−1.0 pp, budget 1.0) had p99 −55%.

Consequence — a structural immunity, not just a noisy metric. Because (i) the p99 tail is set by cold-document first-compute that no lossless retention can touch (§5.2, above) and (ii) the tail is measurably unlinked from the hit gain (Table 3), goodput@SLO on this workload is immune to the entire retention/eviction mechanism class — not only to our mechanism, and not only because the metric is noisy. Even an oracle (Bélády) retention policy, which by definition maximizes the hit-rate lever, would leave the cold-first-compute tail — and therefore goodput@SLO — where it is. The corollary points elsewhere for goodput: the headroom on the SLO-defining tail lives on the cold-miss path (transfer/compute overlap, prefill admission and chunk scheduling, cross-request dedup of near-identical documents), not in what KV is retained.

The immunity generalizes to a testable condition, not just this workload. Retention (and eviction order) can only shrink reuse-recompute — the re-prefill of already-seen prefixes. So goodput@SLO is immune to the retention/eviction class whenever the SLO-defining tail is dominated by cold first-compute rather than reuse-recompute — equivalently, when the largest cold prefills (plus their unavoidable queueing) already exceed the SLO. This workload satisfies the condition decisively: documents run to 183k tokens, 19% of all prompt tokens are irreducibly cold (every conversation's first turn plus 38% single-turn conversations), and the observed p99 stays ≥ 8 s across every hit-rate change we induced (Table 3) while the p50 stays sub-second — i.e. the median request is a cheap cached continuation and the tail is a handful of expensive cold prefills that no lossless cache can avoid. The immunity would relax only under conditions we did not test but can name precisely: (a) a looser SLO (or a mean/p50-TTFT SLO) that absorbs the largest cold prefill, or (b) a reuse-recompute-dominated tail — a tighter cache or a lower cold-document fraction, so that evicted-then-reused continuations, not cold documents, become the slowest requests. Case (b) is the same undersized-cache axis on which §7 predicts the hit gain itself grows: retention regains traction on goodput exactly where the tail stops being cold-bound. This turns the negative into a positive design rule — match the mechanism class to what sets the tail: retention for reuse-recompute tails, the cold-miss path for cold-first-compute tails.

6  Related work

Strata (2025) attacks the data plane and scheduler: GPU-assisted I/O to defragment transfers and cache-aware scheduling to overlap load stalls with compute, making a loading-bound system compute-bound. It does not prevent the eviction that turns a reload into a recompute, and its data-plane fix (the kernel I/O path) is unavailable for hybrid-Mamba models, which are frozen to direct/page_first_direct by the Mamba host pool. Mooncake (FAST'25) and AttentionStore use a KV store and scheduling for reuse across requests; LMCache caches/streams KV; the SGLang HiCache blog contributes tiering, write policies, layer-wise load/compute overlap, and L3 prefetch staging. All treat retention as (recency-ordered) eviction plus (optional) prefetch. Our contribution is orthogonal: a scheduler-sourced reuse-intent signal that decides retention under contention, which the above leave to LRU. Classic cache-admission/replacement (TinyLFU, GDSF, 2Q, ARC) operates on recency/ frequency features; we instead use an exact, workload-structural signal (in-flight continuation).

7  Limitations & when it fails

  • Modest, node-dependent magnitude. The hit gain is small and node-systematic (n=4: +0.1–2.8 pp, mean ≈+1.4; ≈+0.25 pp on ondem-2, ≈+2.5 pp on nodes 0-3/1-2) — far below the oracle gap — because the exploitable server-queue signal is thin and its size tracks queue depth, which differs by node. Where it did not crash it was non-negative, but it is neither robust nor node-independent, so we do not claim a precise or portable number.
  • The client think-gap is not server-realizable. A prefix evicted during the client's think/send gap (before its next turn reaches the server) cannot be protected by a server-queue signal. The obvious fix — retain every recently-finished conversation for a horizon — hurts (§5): it spends scarce L2 on conversations that are never reused. Closing this gap would require a session-level "will-continue" hint from the client/router that the serving layer does not have.
  • Capacity. When the pending set exceeds the L2 pin budget, only a subset is protected; the gain degrades gracefully to LRU (never worse — pinning is bounded and released on admission/abort).
  • Single-turn / low-reuse workloads. If most conversations are one-shot, there is little pending reuse to protect and the mechanism is a safe no-op.
  • Generality: the gain should grow where the cache is undersized. Our measured gain is small because this system's L1+L2 (~10.7M tok) captures most of the workload's (concentrated) reuse (hit ~0.67), so little reused KV is ever at risk of eviction. As the cache shrinks relative to the working set, more reused KV becomes evictable-then-reused and the exploitable set grows — the simulator's LRU-vs-Bélády gap widens from ~7 pp at 10.7M to ~23 pp at 8M (Fig 2). We therefore expect pending-aware retention to matter more on tighter 2-tier provisioning (smaller host DRAM, larger or less-concentrated working sets, or more aggressive L1 occupancy under load). We did not measure undersized-cache regimes, and — per §2.5, where single-tier sim magnitudes did not transfer to the real 2-tier system — we state this as a qualitative direction only, not a quantified prediction.
  • Metric. On this workload goodput@SLO is not just variance-dominated at the boundary — it is structurally immune to the retention/eviction class (§5.2, Table 3): the SLO-defining p99 tail is cold-first-compute-bound and empirically decoupled from the hit gain (r²≈0.09), so even oracle retention leaves it unchanged. We report it but rely on hit-rate/throughput. This is a property of a cold-miss-dominated tail under a p99 SLO; a different SLO (e.g. mean or p50 TTFT), a reuse-heavier workload with fewer cold first-turns, or a tighter cache could make goodput@SLO responsive to retention again — the immunity is scoped to this cold-tail-dominated regime, not universal.
  • The sim's scheduler-coupling does not transfer to real hit (measured, §2.5). §2.4's single-tier simulation predicts a large FCFS eviction gap that prefix-aware scheduling closes. The same-node FCFS-vs-LPM A/B on the 122B system refutes the hit half of that prediction: real hit is scheduler-insensitive (Δ<0.5 pp at every rate), because the 2-tier host absorbs eviction order — LPM only worsens the p99 tail. We report this refutation of our own sim rather than the sim's optimistic magnitude. It does not affect the measured contribution (retention's ~1–2 pp is a real, lossless FCFS-native gain) and it sharpens the thesis (retention, not scheduling, is the hit lever). The arrival-order part of the analysis — the recency-inversion ρ=+0.81 (which needs only the request order, not the tier model) that makes the pending signal well-targeted — does transfer. We confirmed the pin's gain is scheduler-independent: a same-node v1-under-LPM A/B gave +0.15–0.77 pp across rates (smaller than under FCFS, consistent with LPM's shorter pending window). One caveat: ρ=+0.81 is computed under the FIFO closed-loop arrival model (matching FCFS + the harness), not extracted from real server logs; measuring it on production request timelines is future work.
  • Eviction-interaction crash — unresolved, and it sinks the mechanism. Holding a host lock across device eviction leaves the radix tree in a state the write-through delete-entirely path mishandles, tripping assert v==node. This is not confined to the rejected post-completion variant: the shipped queued pin (v1) itself crashed the scheduler (all 8 TP ranks) at λ=7 on a third node at 26 concurrent pins; the clean runs on the first two nodes (≤6 pins) were luck, so v1 is unsafe once pin counts climb (which is node-dependent, §5.2). We attempted two targeted fixes; a stress test (v1 at max pin budget, forcing ~20 concurrent pins) shows neither is sufficient. (1) A tombstone guard (leave a node with surviving host-only children in the tree rather than unlinking it) — the assertion still fires on a childless node. (2) A consistency fix that drops a node from both evictable-leaf sets at every unlink (so the driver, which snapshots the device-leaf set and re-checks membership, cannot re-select a removed node) — v1 crashed anyway, and the trace localizes it to the node's first eviction (_evict_device_leaf → _remove_leaf_from_parent, after both discards run), where parent.children[key] is already not this node. So the corruption is deeper than eviction-set bookkeeping: the node's parent pointer and its parent's children map are inconsistent before eviction — i.e. host-pinning corrupts the radix tree during insertion/split/match, not just during eviction. Fixing that requires reworking the host-lock × tree-mutation interaction, which we have not cracked. We deliberately did not ship a speculative patch nor weaken the assertion (it guards real corruption). v1 is therefore unsafe at high load (≥~20 concurrent pins), and two fixes did not resolve it — this is the study's core negative result, not a minor edge case. Making the pin safe (then re-testing whether any gain survives above the ~0.9 pp noise floor) is the concrete future-work path this result defines.
