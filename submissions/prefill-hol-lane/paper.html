Abstract

PENDING data-driven framing. Skeleton: Modern LLM servers chunk long prefills to avoid stalling decode (Sarathi-style). We show this leaves a second, unaddressed pathology on heavy-tailed conversational workloads: a single cold mega-document (up to 192K tokens) monopolizes the per-iteration prefill token budget for tens of consecutive iterations, head-of-line-blocking every request queued behind it — the dominant contributor to the p99 TTFT tail that defines goodput@SLO. We introduce the reserved short-prefill lane, a non-preemptive, lossless scheduling primitive that holds back a small slice of the prefill budget so short waiting requests prefill alongside an in-flight mega-document, rather than waiting behind it. 1 Introduction

The headline metric on our fixed evaluation is goodput@SLO: the maximum Poisson request rate sustaining p99 TTFT ≤ 8 s. A companion study (Paper 1, prefill-slo-tail) established that this tail is dominated by cold, first-sight prefill of a heavy-tailed document distribution, and that the tail is metastable/variance-dominated near the knee. This paper asks a sharper, mechanism-level question the first study left open: within that cold-prefill tail, how much is a request's own prefill versus queueing behind other requests' prefill, and can a lossless scheduler reduce the latter?

Contribution bullets (finalize wording with results):
  • Diagnosis. We quantify inter-prefill head-of-line (HOL) blocking on the real workload: a chunked mega-document consumes the entire per-iteration prefill budget, stalling all waiting requests for O(doc_len / chunk) iterations.
  • Mechanism. The reserved short-prefill lane — a small held-back budget slice that lets short waiting requests prefill alongside a mega-document. Non-preemptive, lossless, opt-in (one server flag).
  • Evidence. Same-node median-of-k A/B vs both FCFS and SRPF baselines; p99 TTFT distribution shift; goodput@SLO; RESERVE ablation; per-request attribution; losslessness. [pending]

2 Motivation

2.1 A heavy-tailed cold-document workload

The evaluation workload (mooncake_mix_v1.jsonl, multiturn) has a strongly heavy-tailed turn-0 document-token distribution: median ≈ 16.7K, p99 ≈ 65.6K, and a maximum of 192,542 tokens, amid many small follow-on turns. At the fixed --chunked-prefill-size 6144, the largest document requires ⌈192542/6144⌉ ≈ 32 prefill iterations to complete.

2.2 Inter-prefill head-of-line blocking (code-verified)

The scheduler admits at most one chunked (partially prefilled) request at a time. In Scheduler.get_new_batch_prefill, an in-flight chunked request is extended first via PrefillAdder.add_chunked_req, which claims min(rem_chunk_tokens, rem_total_tokens) — the entire 6144-token budget for a mega-document mid-prefill. This drives rem_chunk_tokens → 0, so the subsequent admission loop (add_one_req) returns NO_TOKEN for every waiting request. Consequently, for the ~32 iterations a 192K document takes, no other request can begin prefill: a request arriving in that window waits ~32 × (per-iteration time) ≈ several seconds before its first token — an inter-prefill HOL delay distinct from its own (possibly tiny) prefill cost.

3 Design — the reserved short-prefill lane

The mechanism is a single invariant added to the prefill-budget split. Each prefill iteration has a token budget B (= chunked-prefill-size). When a chunked (large) request is in flight and the waiting queue is non-empty, we cap that request's contribution at B − R instead of B, reserving R tokens. The existing admission loop then admits short waiting requests (input ≤ R) as non-chunked prefills in the same iteration, so they are served immediately rather than after the mega-document completes.

# in PrefillAdder.add_chunked_req, before choosing the chunk length:
_rem = min(rem_chunk_tokens, rem_total_tokens)          # stock: full budget B
cand = len(req.full_untruncated_fill_ids) - len(req.prefix_indices)   # tokens left in this doc
if reserve > 0 and waiting_queue_len > 0 \
   and cand > _rem - reserve and _rem - reserve >= page_size:
    _rem = _rem - reserve          # hold back R for short waiting reqs; doc keeps >= 1 page of progress
new_len = min(cand, _rem)          # doc prefills B-R this iter (vs B); finishes in slightly more iters

Single-chunked-request invariant. The engine permits only one chunked request at a time (Scheduler asserts chunked_req is None before adopting a new one). The reserved budget must therefore admit only short, whole-sequence requests; a long waiting request is not allowed to start a second chunked prefill (guarded in add_one_req by has_chunked_req). This is central to correctness — without it, leftover budget would start an illegal second chunked prefill.

Losslessness. Only the per-iteration token budget split changes. Every token of every request is still prefilled, in-order within each request, producing identical outputs. The mega-document simply completes over slightly more iterations (⌈doc/(B−R)⌉ vs ⌈doc/B⌉). With R = 0 the code path is byte-identical to stock.

Why it is not shortest-first. Unlike SRPF/SJF, the lane does not reorder the queue and does not starve the mega-document — the large document keeps making forward progress every iteration. It is a fair budget reservation, orthogonal to queue ordering.

The distributions are disjoint: every reserve=2048 run (min 29852 ms) has a worse p99 than every reserve0 run (max 26539 ms), while the median TTFT is consistently lower — an unambiguous separation on both axes.

At λ=5 the request throughput achieved is only ~3.2–3.5 (≪ 5): the node is saturated and the prefill queue grows. Here the reserve worsens the p99 tail by ~75% while improving the median by ~18%. This is the mechanism doing exactly what it is designed to — rescuing short (HOL-victim) requests, which pulls the median down — but the p99 tail at λ=5 is not HOL victims; it is the cold mega-documents' own prefill. Capping their per-iteration chunk (6144→4096) makes each mega-document take ~1.5× more iterations, which under saturation lengthens the congestion window and pushes the tail up. The reserve improves the median but cannot improve — and at saturation worsens — the goodput p99, because the tail is the cold-document prefill floor, not inter-prefill queueing. This is a mechanism-level corroboration of Paper 1's finding that the goodput tail is lossless-irreducible cold-prefill (K·t), not schedulable.

6 Related work

Chunked prefill / Sarathi-Serve (OSDI'24), vLLM. Introduced splitting long prefills into token-budget chunks and piggybacking decode to eliminate prefill→decode stalls. It does not reserve budget for other waiting prefills; a single large chunked prefill can still monopolize the prefill budget across its chunks. We target the residual inter-prefill HOL that chunked prefill leaves.

FastServe. Preemptive MLFQ scheduling with skip-join to bound request-level HOL. The reserved lane is non-preemptive — no eviction/recompute — a within-iteration budget split.

SRPF / SJF (shortest-first). Reduce mean/tail by serving short jobs first, but starve the long cold documents that themselves define the p99. The reserved lane neither reorders nor starves. (Charter note: plain SRPF/SJF are considered non-contributions; our mechanism is distinct on exactly this starvation axis.)

Mooncake (FAST'25), disaggregated prefill/decode. Separates prefill and decode pools across nodes; orthogonal to single-node intra-iteration prefill budgeting.

Fair queuing / DRR. The reserve is fair-queuing-flavored at the prefill-token-budget level; the contribution is the diagnosis (goodput@SLO tail = inter-prefill HOL on a heavy-tailed cold-doc workload) and the lossless, non-starving collapse of the victim tail, evidenced by beating both FCFS and SRPF.

7 Limitations & when it fails

PENDING quantification. The reserve slows the mega-document by a factor B/(B−R) in prefill iterations; if the p99 is bounded by a mega-document's own prefill (not its victims' queueing), the lane cannot help — that is the bounded-negative outcome, itself a result. Reserve size trades victim relief against mega-document slowdown (ablation).
